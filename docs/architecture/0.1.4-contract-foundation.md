# TERMAX 0.1.4: Contract Foundation

Status: proposed implementation specification  
Target branch: `development/0.1.4-contract-foundation`  
Compatibility baseline: TERMAX 0.1.0 remains protected and unchanged.

## 1. Purpose

Establish small, versioned contracts that let the next TERMAX runtime evolve without coupling plugins, agents, workers, storage backends, visual components, and execution policy to one another.

This milestone defines interfaces and validation rules. It does not claim that the 0.2.x runtime, agent system, distributed execution, or security isolation already exists.

## 2. Non-negotiable compatibility and safety rules

- Do not overwrite the installed `~/.local/share/termax` or `~/.local/bin/tx`.
- Develop in a separate branch and staging directory.
- Preserve existing configuration and user data; migration is preview-first.
- Optional dependencies must not prevent core startup.
- Plain-text operation remains supported when terminal graphics are unavailable.
- A subprocess or Proot environment is not represented as a strong security sandbox on ordinary Termux.
- Capability declarations describe requested authority; they do not grant authority.
- Policy evaluation and execution approval remain separate from agent reasoning.
- A completed task is not considered verified until its verification policy passes.
- Rollback is promised only for reversible effects; otherwise define compensating actions and disclose residual effects.

## 3. Contract package layout

Initial proposed package boundaries:

```text
termax/
  contracts/
    __init__.py
    version.py
    identity.py
    task.py
    event.py
    artifact.py
    worker.py

  security/
    __init__.py
    policy.py
  transactions/
    __init__.py
    journal.py
  config/
    schema.py
tests/
  contracts/
```

The first implementation should use the Python standard library wherever practical. Add a third-party dependency only when a demonstrated requirement justifies it.

## 4. Shared identity and versioning

Every durable entity receives a stable identifier independent of its display name or filesystem path. Contract versions use an explicit major/minor scheme.

- Major version: incompatible shape or semantic change.
- Minor version: backward-compatible optional fields or new enumerated values where consumers can safely reject unknown values.
- Producers include contract version and producer identity.
- Consumers validate before acting and reject unsupported major versions.

Unknown fields should be preserved by import/export tooling where safe, but must never silently weaken security policy.

## 5. Task contract

A task is a declared unit of work with an objective, scope, dependencies, expected outputs, and a verification policy.

Minimum fields:

```json
{
  "schema_version": "1.0",
  "task_id": "stable-id",
  "parent_task_id": null,
  "objective": "Human-readable objective",
  "status": "created",
  "dependencies": [],
  "required_capabilities": [],
  "input_artifacts": [],
  "expected_outputs": [],
  "verification_policy": "default",
  "retry_policy": "safe_only"
}
```

Initial lifecycle:

`CREATED -> PLANNED -> VALIDATED -> READY -> RUNNING -> COMPLETED -> VERIFIED -> CLOSED`

Terminal or exceptional states include `BLOCKED`, `FAILED`, `CANCELLED`, and `REQUIRES_APPROVAL`. `COMPLETED` and `VERIFIED` are deliberately distinct.

## 6. Event contract

Events are append-oriented observations, not implicit commands.

Minimum fields:

- `event_id`
- `timestamp` (UTC ISO 8601)
- `severity`
- `source`
- `event_type`
- `message`
- optional `task_id`, `trace_id`, `agent_id`, `worker_id`, `workspace_id`, `transaction_id`
- `attributes` and `artifact_refs`

Severity values: `DEBUG`, `INFO`, `NOTICE`, `WARNING`, `ERROR`, `CRITICAL`.

Events must not contain secret values. Redaction is applied before persistence and export.

## 7. Artifact contract

Artifacts are immutable, versioned outputs exchanged between tasks and workers.

Minimum manifest fields:

- `artifact_id`, `version`, `media_type`, `size_bytes`
- `sha256`
- `producer_id`, `task_id`
- `classification`
- `created_at`
- `retention_policy`

A reference to an artifact is not an access grant. The artifact registry must authorize access independently. Checksum mismatch means quarantine and rejection, not best-effort use.

## 8. Worker contract

Workers advertise capabilities and limits; the scheduler selects a worker only after policy checks.

Initial interface methods:

- `capabilities()`
- `health_check()`
- `prepare(task, scope)`
- `execute(task, inputs)`
- `cancel(task_id)`
- `collect_artifacts(task_id)`
- `cleanup(task_id)`

Worker profiles (`native`, `trusted`, `development`, `experimental`, `restricted`, `remote`) are policy configurations, not claims of operating-system isolation.

## 9. Capability and policy contract

Capability requests are default-deny and scoped to an identity, resource, task, and expiry.

A grant record should include:

- `grant_id`, `principal_id`, `task_id`
- `capabilities`
- `scope` (for example, explicitly allowed filesystem paths)
- `restrictions`
- `expires_at`
- `approval_reference`

Policy outcomes:

`ALLOW`, `DENY`, `REQUIRE_APPROVAL`, `REQUIRE_VERIFICATION`, `QUARANTINE`.

Agents and plugins cannot self-grant capabilities or expand delegated scope. A declaration is a request, not permission. Execution must pass through the policy and execution gateway.

## 10. Transaction journal contract

Risky mutations follow:

`PREPARE -> PREFLIGHT -> CHECKPOINT -> APPROVE -> EXECUTE -> VERIFY -> COMMIT`

Failure routes to `RECOVER` or `COMPENSATE`, depending on reversibility.

Journal entries record transaction ID, actor, target scope, planned operations, checkpoint references, approval reference, before/after integrity evidence, outcome, and recovery notes. Never claim atomic rollback for external side effects that cannot be reversed.

## 11. Configuration resolution contract

Configuration precedence, from lowest to highest:

1. Built-in defaults
2. Device configuration
3. User configuration
4. Active profile
5. Project configuration
6. Workspace configuration
7. Session configuration
8. Explicit CLI overrides

Security policy has a separate restrictive precedence and cannot be weakened by a higher-precedence ordinary configuration layer. The loader produces an immutable effective snapshot with each value's source and validation result. Invalid configuration fails closed for the affected feature and reports a useful diagnostic.

## 12. Initial verification gates

The first contract implementation is acceptable only when tests cover:

- valid and invalid schema instances;
- missing required fields and unknown optional fields;
- unsupported major contract versions;
- invalid task state transitions;
- duplicate event and task identifiers;
- artifact checksum mismatch and quarantine;
- capability default-deny, scope mismatch, expiry, and delegation limits;
- transaction failure before and after mutation;
- configuration precedence and policy non-weakening;
- redaction of secret-like values from event output;
- compatibility with the supported Python version on Termux.

## 13. Explicitly out of scope for this milestone

- Full autonomous or multi-agent runtime.
- Claims of strong sandboxing on Termux.
- Mandatory remote execution or external AI provider.
- Mandatory vector database or graph database.
- Always-on background daemon.
- Automatic replacement of the existing 0.1.0 installation.
- Automatic migration of shell startup files or credentials.

## 14. Next implementation sequence

1. Add typed contract models and version constants.
2. Add deterministic validators and transition tests.
3. Add policy decision interface with a default-deny reference implementation.
4. Add event serialization and redaction tests.
5. Add transaction journal model and recovery-state tests.
6. Add config resolver with precedence/provenance tests.
7. Run tests in isolated staging on the supported Termux/Python matrix.
8. Review the diff and compatibility report before any installation or promotion.
